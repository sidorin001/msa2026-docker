# Проверки

Python 3 обязателен. Отдельному `smoke.py` достаточно 3.6+; остальному набору нужен Python 3.10+. CI проверяет 3.12; отдельного полного прогона на Ubuntu 18.04/Python 3.6 не выполнялось. API/lifecycle/RR-тесты используют только stdlib хоста. Приложения запускаются в Docker. На Linux используйте `python3`, поскольку `python` может запускать Python 2.7; в Windows можно использовать `py -3`.

- `python3 tests/smoke.py --base-url http://localhost:8080` — только чтение: точные 4/10 seed-данные, маршруты, агрегирование, фильтр, 400/404/405/HEAD и пустая группа. До 120 секунд ожидания готовности.
- `python3 tests/integration.py` — **только одноразовый стенд на порту 8080**: проверка семи контейнеров, изоляции сетей/портов/ролей, runtime UID/отсутствия компилятора, отказов БД, восстановления и пересоздания с сохранением volumes. Запрещённые SQL-операции должны завершаться отказом.
- `python3 tests/http_response.py` — прямые HTTP-запросы к Service1 из сети контейнеров: JSON и заголовки, 400/404/405, отсутствие дублированных заголовков, HEAD без тела и с Content-Length соответствующего GET. Проверка обходит Caddy, чтобы прокси не маскировал ошибки HTTP-ответа.
- `python3 tests/replicas.py` — **разрушительный lifecycle-тест одноразового стенда**: 20 запросов по одному HTTP-соединению чередуют A/B 10/10; тот же тест агрегирования; stop/start и pause/unpause каждой реплики; отказ обеих; исключение живой реплики по HTTP 503 readiness; отсутствие возврата без успешных проверок; восстановление общей db2 и отсутствие повторного seed. Обнаружение/возврат ожидаются bounded polling с deadline 30 секунд.
- `python3 tests/pgadmin_browser.py` — Playwright 1.56.0/Chromium: вход через /pgadmin, статика и подтверждение завершённого подключения к обеим БД. Перед запуском: `python3 -m pip install playwright==1.56.0`, `python3 -m playwright install --with-deps chromium`. Читает тестовый `.env` с простыми некавыченными значениями. Снимки — `test-results/`.

`replicas.py` временно применяет `tests/compose.readiness-test.yaml`, монтируя Python-wrapper и локальные флаги `.local/readiness/a,b`. Wrapper изменяет только `/ready`, оставляя процесс и Items API доступными. В обычном образе/Compose этого кода и управляющего endpoint нет. В конце восстанавливаются обычные entrypoint реплик. Не запускайте эти проверки на общем/рабочем окружении.

CI собирает оба образа, проверяет Compose/Caddy, API, lifecycle, реплики и pgAdmin. Пароли генерируются случайно. В конце удаляет **свои** одноразовые volumes. Не копируйте cleanup на стенд с нужными данными. Успех тестов не означает отсутствия коротких ошибок запросов между физическим отказом и активным обнаружением Caddy; после обнаружения нездоровая реплика не должна получать новые запросы.
