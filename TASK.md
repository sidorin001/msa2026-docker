# Техническое задание: msa2026-docker

Дата создания: 15 ноября 2026 года. Редакция: 17 ноября 2026 года. Документ предназначен для агента разработки.

Целевой репозиторий: https://github.com/sidorin001/msa2026-docker

## 1. Цель и статус решений

Подготовить учебный демонстрационный проект: Service1 на C++17 с фреймворком Qt и сборкой CMake, Service2 на Python в двух параллельных репликах. Service1 использует db1; обе реплики Service2 используют одну общую db2. Сервисы взаимодействуют по HTTP; единая точка входа и балансировщик — Caddy, администрирование БД — pgAdmin. Окружение собирается и запускается Docker Compose.

**Согласовано:** одна реплика Service1 и две реплики Service2; две БД db1/db2, причём db2 общая для обеих реплик Service2; pgAdmin и Caddy gateway; Service1 на C++17/Qt/CMake; Service2 на Python; multi-stage Dockerfile для каждого сервиса; балансировка Caddy по Round Robin с проверкой здоровья каждой реплики, исключением неработающей и возвратом только после успешной проверки; версия API в URL `/api/v1`; сущности groups/items с полем name; чтение списков и отдельных записей; получение элементов группы через Service1; доступ каждого сервиса только к своей БД; четыре группы и распределение элементов 2/3/5/0; целевой GitHub-репозиторий.

**Дополнение от 17 ноября 2026 года — реплики:** две реплики Service2 запускаются одновременно из одного образа и обслуживают один контракт API. Рекомендация: явные Compose-сервисы `service2-v1-a` и `service2-v1-b`, чтобы Caddy проверял два отдельных стабильных адреса. Вместе с `service1-v1`, `db1`, `db2`, `pgadmin`, `gateway` это семь контейнеров. `service2-v1` далее обозначает логический сервис. Новая редакция заменяет прежнее требование о шести контейнерах и единственном экземпляре Service2. Численные параметры healthcheck и маршрут внутренних вызовов через балансировщик ниже — рекомендуемые решения.

**Изменение от 17 ноября 2026 года:** требование о двух C++/CMake-сервисах заменено разными технологическими стеками. Qt обязателен для Service1; Python обязателен для Service2. Конкретные версии Qt/Python, модули Qt и Python-фреймворк ниже остаются рекомендациями. Текущий запрос изменяет ТЗ; перенос существующего кода на новые стеки выполняется отдельным заданием. Предыдущий отчёт `VALIDATION.md` относится к прежней реализации и не подтверждает соответствие этой редакции.

**Рекомендуемые значения (не были отдельно утверждены):** библиотеки и их версии, версии образов, порты, имена БД и пользователей, формат JSON и ошибок, тайм-ауты, параметры и путь healthcheck, конкретная сетевая схема, pgAdmin под `/pgadmin/`, автоматические проверки и способ публикации. Само наличие healthcheck реплик Service2 и управление их участием в балансировке обязательны. Ниже рекомендуемые решения обозначены «Рекомендация». Агенту следует использовать их как исходные значения, документировать окончательный выбор и не выдавать их за ранее согласованные требования.

Объём: только операции чтения. POST/PUT/PATCH/DELETE, API v2, Kubernetes, брокеры, ORM и пользовательская авторизация не входят в текущую реализацию. Локальный HTTP-стенд не предназначен для публикации в открытый интернет без отдельной настройки защиты.

## 2. Архитектура

```text
Клиент → gateway (Caddy)
          ├─ /api/v1/groups и дочерние пути → service1-v1 → db1
          │                                  └─ HTTP → gateway /api/v1/items?group_id=...
          ├─ /api/v1/items и дочерние пути → Round Robin по здоровым репликам
          │                                  ├─ service2-v1-a ─┐
          │                                  └─ service2-v1-b ─┴─ общая db2
          └─ /pgadmin/ → pgadmin → db1, db2
```

- `service1-v1` на C++/Qt владеет groups и предоставляет агрегирующий маршрут элементов группы.
- Логический `service2-v1` на Python владеет items и фильтрует их по `group_id`. Обе реплики используют одинаковые код, версии зависимостей, настройки схемы и общую db2; различаются только идентификатором экземпляра.
- Рекомендация: Service1 обращается к `http://gateway:80/api/v1/items?group_id={id}` через DNS Compose, чтобы его запросы проходили через тот же пул Round Robin и healthcheck, что и внешние запросы. Эта схема изображена выше и заменяет прежний прямой вызов единственного Service2. Не закреплять агрегирование за репликой A или B. Если агент выбирает отдельный внутренний listener Caddy, он должен обеспечить эквивалентные балансировку и healthcheck и описать это в README; дополнительный балансировщик-контейнер не требуется.
- Service1 не подключается к db2, Service2 не подключается к db1. pgAdmin имеет административный доступ к обеим БД.
- Имена Compose отражают поддержку API v1. Каталоги исходников: `service1/`, `service2/`. Версия приложения и версия схемы БД не обязаны совпадать с версией REST API.
- Реплики Service2 не имеют собственных копий PostgreSQL или отдельных volumes данных. Seed db2 выполняет её контейнер один раз при пустом volume; запуск второй реплики не создаёт ещё 10 items. Отказ одной реплики покрывается другой; общая db2 остаётся общей зависимостью, её репликация в это ТЗ не входит.

## 3. Контракт REST API

| Метод | Внешний путь | Обработчик | Результат |
|---|---|---|---|
| GET | `/api/v1/groups` | Service1 | Все группы |
| GET | `/api/v1/groups/{id}` | Service1 | Одна группа |
| GET | `/api/v1/groups/{id}/items` | Service1 → Service2 | Элементы группы |
| GET | `/api/v1/items` | Service2 | Все элементы |
| GET | `/api/v1/items/{id}` | Service2 | Один элемент |
| GET | `/api/v1/items?group_id={id}` | Service2 | Элементы с указанным group_id |

Префикс `/api/v1` сохраняется при проксировании. Старые `/context/` и неверсионированные пути не реализовывать как дополнительные API.

### Рекомендуемый контракт ответов

- JSON, `Content-Type: application/json`; строки UTF-8.
- Группа: `{"id":1,"name":"Group 1"}`.
- Элемент: `{"id":1,"group_id":1,"name":"Item 1"}`.
- Списки — массивы объектов без дополнительной оболочки; сортировка по `id ASC`.
- Успех: `200`. Существующая группа без элементов: `200` и `[]`.
- Service1 сначала проверяет существование группы в db1. Для отсутствующей группы агрегирующий маршрут возвращает `404`, не вызывая Service2.
- Фильтр Service2 по положительному `group_id`, для которого нет элементов, возвращает `200` и `[]`: Service2 не проверяет существование группы в db1.
- Отсутствующая отдельная запись: `404`; некорректный id/group_id, ноль, отрицательное значение или переполнение допустимого диапазона: `400`.
- Неизвестный путь: `404`; неподдерживаемый метод известного ресурса: `405` с `Allow: GET` (HEAD/OPTIONS допускаются при явном документировании).
- Недоступность собственной БД: `503`; неожиданная внутренняя ошибка: `500`.
- Для агрегирования: ошибка соединения или невалидный/неуспешный ответ Service2 — `502`; истечение времени ожидания — `504`. Не превращать сбой зависимости в пустой список.
- Ошибки сервиса: `{"error":{"code":"not_found","message":"Group not found"}}`. Не включать SQL, пароли, строки подключения или внутренний stack trace. Ошибки маршрутизации Caddy могут иметь отдельный простой формат, описанный в README.
- Внешний Caddy при недоступном upstream возвращает контролируемую ошибку `502/503`, без требования унифицировать её JSON с ошибками приложения.
- При исключении одной реплики Service2 запросы продолжают обслуживаться оставшейся здоровой репликой. При отсутствии здоровых реплик Caddy возвращает ограниченную по времени ошибку `502/503`; агрегирование Service1 отображает её в `502`, либо в `504` при истечении своего тайм-аута. Пустой список не является заменой ошибки зависимости.

## 4. Схемы и начальные данные

Рекомендация: `INTEGER` для положительных идентификаторов, первичные ключи; `name TEXT NOT NULL`; `items.group_id INTEGER NOT NULL CHECK (group_id > 0)` и индекс по `group_id`.

```sql
-- db1
CREATE TABLE groups (
  id INTEGER PRIMARY KEY CHECK (id > 0),
  name TEXT NOT NULL
);
-- db2
CREATE TABLE items (
  id INTEGER PRIMARY KEY CHECK (id > 0),
  group_id INTEGER NOT NULL CHECK (group_id > 0),
  name TEXT NOT NULL
);
CREATE INDEX items_group_id_idx ON items(group_id);
```

`items.group_id` — логическая ссылка на `groups.id`. Обычный PostgreSQL FOREIGN KEY между независимыми экземплярами db1/db2 не создавать. В этом проекте согласованность обеспечивается начальными данными; распределённые записи не требуются.

| group.id | Рекомендуемое name | ID элементов | Количество |
|---|---|---|---:|
| 1 | Group 1 | 1, 2 | 2 |
| 2 | Group 2 | 3, 4, 5 | 3 |
| 3 | Group 3 | 6, 7, 8, 9, 10 | 5 |
| 4 | Group 4 | отсутствуют | 0 |

Рекомендуемые имена элементов: `Item 1` … `Item 10`. Итого строго 4 группы и 10 элементов. Использовать детерминированные ID и SQL-скрипты инициализации, подключённые read-only к `/docker-entrypoint-initdb.d/` соответствующей БД.

Инициализация PostgreSQL выполняется только при пустом каталоге данных. Повторный обычный запуск не дублирует seed и не удаляет данные. README должен различать перезапуск и полный сброс с удалением volumes; команду сброса сопровождать явным предупреждением об удалении данных.

## 5. Реализация и сборка

- **Service1:** самостоятельный CMake-проект на C++17 с использованием Qt для реализации REST-сервиса. Это серверное приложение без графического интерфейса; Qt должен участвовать в обработке HTTP/JSON/сетевого взаимодействия, а не быть формальной неиспользуемой зависимостью.
- Рекомендация для Service1: Qt 6 совместимой с C++17 версии; `QCoreApplication`, Qt HTTP Server (`QHttpServer`), Qt Network (`QNetworkAccessManager`) для вызова Service2, Qt JSON (`QJsonDocument`, `QJsonObject`, `QJsonArray`), Qt SQL с PostgreSQL-драйвером `QPSQL`. Использование cpp-httplib и nlohmann/json более не является рекомендуемым стеком Service1.
- **Service2:** самостоятельный Python-проект. CMake и компиляция C++ для него не требуются. Рекомендация: Python 3.12, FastAPI, Uvicorn и Psycopg 3; эквивалентный Python-стек допускается с обоснованием в README. Версии прямых и транзитивных зависимостей закрепить в lock-файле либо полном `requirements.txt`.
- Рекомендация: CMake не ниже 3.22 для Service1; PostgreSQL 17, Caddy 2, pgAdmin 4. Конкретные совместимые версии Qt, Python, образов и библиотек зафиксировать и проверить при реализации; не использовать `latest`, плавающие ветки Git или непроверенные сочетания версий.
- Для каждого сервиса отдельный multi-stage Dockerfile. **Service1:** build-stage устанавливает компилятор, CMake, Qt и зависимости, собирает бинарник; runtime-stage содержит бинарник, runtime-библиотеки Qt, плагин `QPSQL` с его зависимостями и необходимые файлы лицензий. Проверить нахождение SQL-плагина в контейнере и совместимость ABI стадий.
- **Service2:** build-stage подготавливает закреплённые Python-зависимости (например, wheels или virtualenv); runtime-stage содержит Python-интерпретатор, код сервиса и runtime-зависимости. Не требовать бинарного executable вместо Python-кода; компилятор и build-зависимости в runtime не переносить. Использовать совместимые Python/ОС/архитектуру на обеих стадиях.
- Сборка и запуск через Compose не требуют локально установленных C++/Qt/CMake или Python для сервисов. Python на хосте нужен только при запуске тестов с хоста.
- Рекомендация: непривилегированный пользователь в runtime, exec-form ENTRYPOINT/CMD, корректное завершение по SIGTERM, логирование в stdout/stderr.
- Сервисы слушают `0.0.0.0:8080` внутри контейнера. Параметры БД и URL Service2 передаются окружением; localhost для обращения к соседним контейнерам не использовать.
- Все SQL-запросы с внешними параметрами параметризованы. Валидировать идентификаторы до запроса. В Service1 соблюдать потоковую принадлежность Qt SQL-соединений и Qt Network-объектов; не блокировать главный event loop длительным обращением к БД или Service2. В Service2 использовать соединения/пул согласно модели выбранного драйвера; синхронные обращения не должны блокировать асинхронный event loop.
- При смене фреймворков сохранить контракт раздела 3: в частности, не заменять согласованный `400` на стандартный `422` Python-фреймворка, не менять массивы на оболочки и не добавлять перенаправления путей, маскирующие ошибки маршрутизации. Поведение HEAD/OPTIONS явно документировать и проверять.
- Рекомендация: тайм-аут соединения Service1 с точкой балансировки Service2 — 2 секунды, чтения — 10 секунд; конечный тайм-аут БД. Значения настраиваются. Gateway при обращении к Service1 должен ждать дольше внутреннего тайм-аута агрегирования.
- Рекомендация: `/health` для проверки процесса и `/ready` для проверки собственной БД. Readiness Service1 не должна зависеть от Service2: базовый Groups API обязан работать при остановке обеих реплик. Каждая реплика Service2 обязана предоставлять HTTP endpoint для активной проверки Caddy; рекомендуемый `/ready` возвращает `200` только при готовности обслуживать API с db2 и неуспешный статус при недоступности БД. `/health`, не проверяющий БД, не использовать вместо readiness при выборе реплик.
- Для демонстрации балансировки обеспечить идентификацию обработавшей запрос реплики без изменения JSON-контракта. Рекомендация: окружение `INSTANCE_ID` со значениями `service2-v1-a` / `service2-v1-b`, заголовок ответа `X-Service2-Instance` и идентификатор в логах. Caddy сохраняет этот заголовок; Service1 рекомендуется передавать его в ответе агрегирующего маршрута. Клиент не должен влиять на выбор реплики этим заголовком.

## 6. Compose, конфигурация и доступ

В основном окружении одновременно запущены семь контейнеров: `service1-v1`, две реплики Service2, `db1`, `db2`, `pgadmin`, `gateway`. Рекомендация: `compose.yaml`, Docker Compose v2 и явные сервисы `service2-v1-a` / `service2-v1-b`. Собирать один образ Service2 из `service2/Dockerfile` и запускать из него обе реплики с одинаковыми DB2-параметрами. Не задавать `container_name`, чтобы не блокировать запуск с другим именем проекта. Не подменять два upstream-адреса одной DNS-записью с несколькими IP без доказанной поддержки отдельных активных проверок выбранной конфигурацией Caddy.

### Рекомендуемые параметры .env.example

| Переменная | Значение примера / назначение |
|---|---|
| GATEWAY_BIND | `127.0.0.1` |
| GATEWAY_PORT | `8080` |
| DB1_NAME / DB2_NAME | `groups_db` / `items_db` |
| DB1_APP_USER / DB2_APP_USER | `groups_app` / `items_app` |
| DB1_APP_PASSWORD / DB2_APP_PASSWORD | разные заменяемые значения |
| DB1_ADMIN_PASSWORD / DB2_ADMIN_PASSWORD | разные заменяемые значения |
| PGADMIN_DEFAULT_EMAIL | `admin@example.com` |
| PGADMIN_DEFAULT_PASSWORD | заменяемое значение |
| SERVICE2_BASE_URL | `http://gateway:80` — рекомендуемая точка балансировки для Service1 |
| INSTANCE_ID | отдельное значение для каждой реплики Service2; задаётся в Compose |
| HTTP_CONNECT_TIMEOUT_MS | `2000` |
| HTTP_READ_TIMEOUT_MS | `10000` — ожидание Service1 при вызове через балансировщик |

Внутри сервисов использовать согласованные имена окружения: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `HTTP_PORT`; Compose отображает DB1/DB2-переменные в соответствующий сервис. Для БД внутренний порт `5432`.

- Публикуется только gateway: по умолчанию `127.0.0.1:8080:80`. db1, db2, Service1, обе реплики Service2 и pgAdmin не имеют `ports` на хост.
- Рекомендация: отдельная сеть для gateway и API-сервисов; отдельная сеть gateway↔pgAdmin; отдельные `internal: true` сети db1 и db2. В сети db1 состоят только db1, Service1, pgAdmin; в сети db2 — только db2, обе реплики Service2, pgAdmin. Gateway не включать в сети БД. Все сети объявить явно, избегая общей default-сети для всех контейнеров.
- Сети ограничивают прямую связность, но не являются политикой направлений HTTP. На общей сети API возможна связность всех API-контейнеров; рекомендуемый прикладной маршрут — Service1 → Caddy → здоровая реплика Service2.
- Учётная запись приложения не является суперпользователем и получает только CONNECT, USAGE схемы и SELECT своих таблиц. Административные учётные данные используются только при инициализации и в pgAdmin. Инициализацию ролей реализовать без небезопасной подстановки секретов в SQL.
- Секреты не коммитить: `.env` в `.gitignore`, в `.env.example` только явные демонстрационные заменяемые значения. Не выводить секреты в логи и результаты проверок.
- Рекомендация: именованные volumes для каждой БД и pgAdmin; Caddyfile, SQL и файл определения серверов pgAdmin монтируются read-only.
- Рекомендация: `pg_isready` для БД и `depends_on` с `service_healthy` для соответствующих сервисов. Обе реплики Service2 зависят от одной db2. Не создавать циклическую зависимость запуска Service1 ↔ gateway: readiness Service1 проверяет только db1, Service1 не ожидает gateway при старте. Docker healthcheck проверяет HTTP readiness и реально имеет нужную утилиту в runtime-образе. Приложения корректно обрабатывают временную потерю соединения после запуска: одного depends_on недостаточно. Caddy выполняет собственные HTTP healthcheck каждой реплики; состояние Docker `unhealthy` само по себе не является механизмом её исключения Caddy.
- pgAdmin должен показывать подключения к `db1:5432` и `db2:5432`; допустим импорт `servers.json` без паролей и ручной ввод паролей. Не требовать прямых портов БД на хосте.

## 7. Caddy и pgAdmin

Обязательно настроить два отдельных upstream Service2, `lb_policy round_robin` и активные HTTP-проверки каждой реплики. Неработающая реплика исключается из выбора для новых запросов и остаётся исключённой до успешного прохождения активных проверок; один лишь истёкший таймер или успешный TCP connect не должен возвращать её в пул. Возврат после восстановления автоматический, без перезагрузки Caddy.

Рекомендуемые параметры: `health_uri /ready`, ожидаемый статус `200`, интервал `5s`, timeout `2s`, `health_fails 1`, `health_passes 2` (два последовательных успешных ответа перед возвратом, защита от нестабильного состояния). Это значения для учебного стенда, а не ранее согласованные числа. Ошибка HTTP, timeout и ошибка подключения считаются провалом проверки; перенаправление не считать успешным readiness.

Рекомендуемый фрагмент Caddyfile; итоговую конфигурацию агент проверяет выбранной закреплённой версией Caddy:

```caddyfile
:80 {
    @groups path /api/v1/groups /api/v1/groups/*
    handle @groups {
        reverse_proxy service1-v1:8080 {
            transport http {
                dial_timeout 2s
                response_header_timeout 20s
            }
        }
    }
    @items path /api/v1/items /api/v1/items/*
    handle @items {
        reverse_proxy service2-v1-a:8080 service2-v1-b:8080 {
            lb_policy round_robin
            health_uri /ready
            health_status 200
            health_interval 5s
            health_timeout 2s
            health_fails 1
            health_passes 2
            transport http {
                dial_timeout 2s
                response_header_timeout 5s
            }
        }
    }
    redir /pgadmin /pgadmin/ 308
    handle /pgadmin/* {
        reverse_proxy pgadmin:80 {
            header_up X-Script-Name /pgadmin
        }
    }
    handle {
        respond "Not Found" 404
    }
}
```

Для API не использовать `handle_path`, удаляющий префикс. `/api/v1/groups-extra` и `/api/v1/items-extra` не должны попадать в соответствующие сервисы.

Балансировка выполняется на уровне HTTP-запросов, а не TCP-соединений клиента. При двух здоровых репликах последовательные запросы чередуют upstream; при одной — все новые запросы направляются ей. `/ready` проверяется напрямую на каждой реплике, а не через общий балансируемый URL, и не публикуется как внешний маршрут gateway.

В базовом варианте использовать активные проверки без пассивного `fail_duration`: пассивный таймер сам по себе не выполняет требование о возврате только после успешного healthcheck. Дополнительные passive checks или retries допустимы только при проверенном сохранении этого условия и конечных тайм-аутах. Повторные попытки по умолчанию в примере не включены: между фактическим отказом и его обнаружением healthcheck возможны ошибки отдельных запросов, а уже выполняющийся запрос не переносится автоматически на другую реплику. После обнаружения отказа новые запросы не должны попадать на исключённую реплику.

Тайм-ауты разных участков согласовать с маршрутом Service1 → Caddy → Service2: ожидание Service1 должно быть больше внутреннего timeout Caddy к Service2, а ожидание Caddy к Service1 — больше суммарного времени проверки группы и внутреннего вызова. Рекомендация для этой схемы: timeout Service1 при чтении Service2 `10000` мс и `response_header_timeout 20s` для upstream Service1. Обновить `.env.example` соответственно; прежние `5000` мс для Service1 не считать обязательными.

Рекомендация: pgAdmin работает с внешним префиксом `/pgadmin`, передаваемым через `X-Script-Name`; точную конфигурацию адаптировать к закреплённому образу. Проверить не только стартовую страницу, но и форму входа, cookies, redirects, JS/CSS и открытие обеих БД через прокси. Если требуется удаление префикса перед upstream, сделать это только для pgAdmin и сохранить внешний script prefix. Не считать конфигурацию готовой без браузерной проверки.

Для тестов 25–27 применять bounded polling фактического состояния и серии ответов с конечным deadline, а не произвольный короткий sleep. Рекомендация: deadline 30 секунд для исключения и 30 секунд для возврата при приведённых настройках; учитывать health_timeout, число fails/passes и запас CI. Отдельно проверить timeout проверки (например, приостановкой реплики) и HTTP-ошибку readiness через изолированную тестовую конфигурацию; не добавлять публичный управляющий endpoint отказа в продукт. Healthcheck-запросы не включать в счётчики пользовательского Round Robin, а параллельные внешние/агрегирующие запросы на время точной проверки чередования остановить.
